# WO-156 — Route self-loop guard, wedged-channel recovery, multiview re-apply after Caspar restart

**Status:** Implemented (pending on-hardware verification A156.1–A156.3)
**Priority:** High (on-air incident required a full CasparCG restart)
**Date:** 2026-07-13
**Source:** `work/todos13.07.26` (owner)
**Related:** WO-48 (layer route live source reuse), WO-84 (router refactor), WO-146 (state monitor), WO-151 (multiview timers & sizing), `src/bootstrap/caspar-amcp-watchdog.js`.

---

## 1. Problem (owner-reported incident)

> "I accidentally played route:3 on channel 3 and it somehow blocked the screen 2 (ch3) so I couldn't play the route1 which I intended, and then it made the multiview screen display pgm1 at 1fps even though the actual output on pgm1 was fine. Had to restart caspar for a fix."

> "there should be a multiview 'refresh'/apply after caspar restart."

Playing `route://3` **on** channel 3 creates a self-feedback route producer that wedges the channel in CasparCG (and starved the multiview's route consumers → 1 fps PGM1 cell). Nothing prevents this; recovery required a full Caspar restart; and after a Caspar restart the multiview does not reliably come back.

## 2. Investigation findings (2026-07-13)

### Self-route guard — essentially absent

- Route strings are generated client-side in `client/lib/input-channels.js` (`route://${ch}`, `route://${ch}-${n}` at :19,:25,:48,:73) with no filtering of a screen's own channel.
- Server playout paths that issue `PLAY … route://…` with **no self-reference check**: `src/engine/multiview-apply.js:263`, `src/api/host-operator-fullscreen.js:146`, `src/config/routing-setup.js:306`, and the normal take path `src/api/routes-scene-take.js` → `src/engine/scene-native-fill.js` / `scene-route-deps.js` (which only *orders* same-channel routes at `partitionTakeJobsPlayOrder:88`, never rejects a loop).
- The **only** existing guard is `routeLayerDropAllowed()` in `client/components/scenes-compose.js:94-106`, and it is too narrow: it requires channel **and layer** to match, so a whole-channel `route://3` (layer=null — exactly the incident) passes; and it runs only on the compose-canvas drop. `scenes-editor-deck-drop.js:42-70` and `scene-layer-row.js:181-200` have no guard at all.
- Precedent exists in the codebase: Device View cabling rejects `self_loop` edges (`src/config/device-graph-edges.js:19`, `device-graph-core.js:141`) — the concept just never reached playout.

### Wedged-channel recovery — exists but undiscoverable

`POST /api/clear` with channel + no layer → `clearCasparChannel()` (`src/api/routes-amcp.js:235-242` → `src/engine/caspar-channel-clear.js:44-64`, `CLEAR <ch>` + `MIXER <ch> COMMIT`) tears down every producer on the channel, including a self-route — this would have un-wedged ch3 **without** a Caspar restart. There is no operator-facing "unblock this screen" affordance pointing at it.

### Multiview re-apply after Caspar restart — four gaps

Apply chain today: reconnect `status` event (`index.js:389-424`) → `fetchInfo()` → `onAfterInfoConfigReady` (`index.js:243-244`) → `setupAllRouting()` → multiview re-apply at `src/config/routing-setup.js:311-315`.

1. **Re-apply hinges on `wasConnected` toggling false→true** (`index.js:394`). If the restart doesn't produce a clean disconnect event first, `fetchInfo()` is skipped and the multiview is never re-applied.
2. **State-source mismatch:** reconnect re-applies `ctx._multiviewLayout` (singular; set at boot `index.js:130` / WS sync `ws-server.js:349`), but `POST /api/multiview/apply` writes `ctx._multiviewLayouts[n]` (plural) and **never updates the singular** (`src/api/routes-multiview.js:53-57`) — the reconnect can re-apply a stale boot layout.
3. **Only multiviewer n=1 is re-applied** (`routing-setup.js:311` reads only the singular layout).
4. **Silent failure:** the re-apply sits in `try { … } catch {}` (`routing-setup.js:312-315`) — an error right after restart (channel not ready) is swallowed, no retry.

## 3. Tasks

- [x] T156.1 **Server-side self-route validator (authoritative).** Shared helper next to `parseRouteClip` in `src/engine/scene-route-deps.js`: reject a route whose parsed channel equals the destination channel (whole-channel `route://N` or same layer). Call from `routes-scene-take.js`, `multiview-apply.js:263`, `host-operator-fullscreen.js:146`, `routing-setup.js:306`. Rejection returns a clear API error (surfaced as toast), never a silent skip on the take path. Decide with owner whether cross-channel *cycles* (A routes B, B routes A) are also rejected or just warned.
- [x] T156.2 **Client-side prevention.** Filter a screen's own `route://<ownCh>` out of the source list in `client/lib/input-channels.js`; extend `routeLayerDropAllowed` to catch whole-channel routes (layer=null) and hoist it into `scenes-editor-deck-drop.js`, `scene-layer-row.js`, and multiview cell assignment (`client/components/multiview-editor-canvas-layout.js:44,105`).
- [x] T156.3 **Operator recovery affordance.** "Unblock screen / clear channel" action (per-screen context menu or device view) wired to the existing `POST /api/clear` channel path, with confirm (it drops everything on the channel). Document in the wedged-channel runbook note that a Caspar restart is not needed for this class of wedge.
- [x] T156.4 **Multiview re-apply on reconnect, robustly.** Explicit multiview re-apply in the reconnect branch (`index.js:394`) after INFO settles, iterating **all** persisted multiviewers (`_multiviewLayouts` / persistence keys `multiviewLayout`, `multiviewLayout_<n>`); retry with backoff instead of the swallowed catch (`routing-setup.js:312-315`); log outcome. Fix the state-source mismatch: `routes-multiview.js` keeps `ctx._multiviewLayout` in sync (or better, boot/reconnect reads the plural map as single source of truth).
- [x] T156.5 **Manual multiview refresh button.** Operator-facing "refresh multiview" (owner explicitly asked) — a small UI button hitting the existing `POST /api/multiview/apply` for each configured multiviewer, so a stuck multiview is a one-click fix even if auto-reapply misses.
- [x] T156.6 **Smokes:** validator (self-route rejected on all four paths, legitimate cross-channel routes pass); reconnect re-apply invoked for n>1 layouts and for HTTP-applied layouts (mocked AMCP).
