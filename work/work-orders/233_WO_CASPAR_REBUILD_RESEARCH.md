### Q1 — improved-artnet: what it adds vs the native consumer already in bin/casparcg; dynamic config?

**Headline answer to the owner's key question: NO — improved-artnet is still config-file-only. It does NOT add dynamic AMCP `ADD`/live region updates.** Both the shipped binary's consumer and firecraftgaming's improved-artnet register only `register_preconfigured_consumer_factory(L"artnet", …)` (`src/modules/artnet/artnet.cpp:36`, byte-identical in both trees) — neither calls `register_consumer_factory`, and neither exposes an AMCP `ARTNET` keyword. Fixture rig changes still require editing `casparcg.config` XML and a full server restart in both the current shipped consumer and the improved one. This confirms WO-225's finding and means **WO-228's JS-side hybrid (live-reconfigurable) remains the right interim/primary architecture regardless of the rebuild** — see recommendation below.

**Provenance clarified — this is a real, formally-filed upstream PR, not just a stray fork branch:** `firecraftgaming/caspar-server:improved-artnet` = **CasparCG/server PR #1752** ("Improved artnet consumer," open, filed 2026-05-27, 8 commits, +565/-361 across 5 files, `mergeable_state: clean` against current upstream master). It was filed in response to **issue #1749** ("Bug: ArtNet consumer not rasterizing image correctly") — a real user-reported LED-wall rasterization bug against the exact same consumer this box ships.

**Same source lineage confirmed:** the shipped binary's embedded path `/home/serwer/CasparCG_Enhanced/src/modules/artnet/consumer/artnet_consumer.cpp` (WO-225 finding) matches `CasparCG_Enhanced/src/modules/artnet/` exactly — this clone's copy is **329 lines**, structurally identical to what WO-225 reverse-engineered from binary strings (`average_color`, `compute_rect`, `computed_fixture`, `rect`/`point` structs — all present verbatim in `util/fixture_calculation.h`). **This 329-line version is itself already-merged upstream CasparCG/server code** (`src/modules/artnet` exists on `CasparCG/server:master` today, confirmed via GitHub contents API), inherited by Enhanced from a shared ancestor, not something `serwer`/gmeisel01 wrote themselves.

**What improved-artnet changes (diff vs the shipped 329-line version, `artnet_consumer.cpp` grows to 757 lines, `+565/-361` per PR #1752 diffstat):**
| Capability | Shipped (Enhanced, 329 ln) | improved-artnet (757 ln) |
|---|---|---|
| Sampling method | Manual CPU rect math: `compute_rect()` + `average_color()` walk raw frame pixels per fixture (same category of cost as the current JS `averageRegion()` WO-179 reimplemented by hand) | **Native `sws_scale`** — per-fixture-group `SwsContext` downscales the frame directly to a `cols×rows` BGRA buffer, one pixel per sub-fixture (`computed_fixture_group` struct, `artnet_consumer.cpp`). CMakeLists adds `target_link_libraries(artnet PRIVATE ffmpeg)`. **This is the exact "sws_scale native averaging" idea WO-225 Q3/WO-228 proposed doing in the JS ingress path — improved-artnet does it natively inside the consumer itself, one layer closer to the render pipeline than even the JS hybrid would reach.** |

| Config schema | `get_fixtures_ptree()` — schema now **fully known from source** (see below) | Same function, extended schema, also fully known from source |

### Q2 — CasparCG_Enhanced: what it changes vs upstream; base version; how far behind

**What it changes (from README.md + CHANGELOG.md + diff):** three features, all it advertises:
1. **Screen consumer** — fixes a GL viewport bug (canvas rendered at native res then stretched, instead of at configured window size) for LED-wall/multi-display spans; adds `<aspect-ratio>` (ratio strings + decimals), `<always-on-top>`, `<borderless>`, `<brightness-boost>`/`<saturation-boost>`, `<enable-mipmaps>`.
2. **OAL system audio consumer** — replaces callback-driven (OpenAL-clock-controlled) dispatch with video-scheduled dispatch (mirrors the DeckLink consumer's approach) + a 75%-correction/1ms-threshold auto-tune loop, fixing gradual audio/video drift on long-running channels.
3. **PortAudio consumer (new module, `dependencies/portaudio/`)** — adds ASIO (Windows) / JACK (Linux) system audio output with configurable channel count, fuzzy-matched device selection, lock-free FIFO ring buffer, same video-scheduled dispatch + auto-tune as the OAL fix.

README states each has "a corresponding pull request open against upstream CasparCG/server" — this fork exists to let users get these three features pre-merge, i.e. **Enhanced is explicitly a staging fork for 3 specific upstream PRs, not a general feature fork** — it was never intended to also carry the artnet consumer as a differentiator (that's just inherited upstream code, see Q1).

**Base version:** diverges from upstream `CasparCG/server:master` at commit **`0a6b136` "chore: Fix boost folder name mismatch (#1693)"**, merged upstream **2026-01-11**. CHANGELOG.md shows this lineage sits between "CasparCG 2.5.0 Stable" and prep-for-2.6 work (`f970e78 chore: prepare for 2.6 development` is in Enhanced's own pre-divergence history) — Enhanced is a **2.6-dev-line** build, not 2.5-stable.

**How far behind current upstream: ~6 months / ~54 commits.** `git log --oneline 0a6b136..HEAD` = 18 commits on Enhanced's `main` (all its own Screen/OAL/PortAudio work, confirmed zero overlap with `src/modules/artnet/`) vs. 62 commits on firecraft's tree from the same base (8 own + **54 which are plain upstream commits merged into `CasparCG/server:master` since Jan 2026 that Enhanced never pulled**). **Enhanced does not appear to track upstream master after its fork point** — it only added its own 3 features on top of the Jan-2026 snapshot. Notable upstream work merged since then that Enhanced is missing (independent of the artnet question): NDI Discovery Server (#1702, merged 2026-03-17), decklink v210 subregion completion (#1700) and VANC fixes, `libpostproc` dependency removal (#1709), FFmpeg 8 support (#1715, Enhanced is still pinned to its pre-fork "minimum ffmpeg 6.1" requirement), decklink keying-capability check (#1722), AMCP-port-bind-to-specific-IP (#1663), a GCC 14 workaround (#1736), an `av_input` teardown fix (#1748), and Vulkan accelerator work (#1677, merged as a large feature-flagged addition). None of this is artnet-related, but it's relevant to "how far behind is it" and to overall rebuild risk/scope.

**"Custom CEF build" — clarified, not what it sounds like.** Checked `BUILDING.md` and `src/CMakeModules/Bootstrap_Linux.cmake`: CEF is **not compiled from source** in either tree. It's consumed as a prebuilt binary two ways: (a) system package `casparcg-cef-142-dev` from `ppa:casparcg/ppa` (Ubuntu only, `USE_SYSTEM_CEF=ON` default), or (b) CMake `ExternalProject_Add` auto-downloads `cef_binary_142.0.17+g60aac24+chromium-142.0.7444.176_linux64_minimal.tar.bz2` from CasparCG's own dependency mirror when `USE_SYSTEM_CEF=OFF`. Both trees are pinned to **CEF 142** (shared pre-fork ancestry — `feat: cef 142` predates the `0a6b136` divergence point in both). The owner's "custom cef build" most likely refers to picking option (b) or manually resolving the PPA/package step on a non-Ubuntu-LTS box, not an actual from-source Chromium build — worth confirming with the owner before the build-plan assumes anything more exotic.

5. **Validate off-box first** — smoke-test the new binary (artnet fixture rig against real hardware if available, DeckLink/NDI/STREAM consumers if those PR fixes were pulled) on the build machine or a disposable target, **not** this live box, before any deployment/swap here. ## What the rebuild obsoletes / what stays

- **WO-229 (native artnet config schema reverse-engineering from binary strings) — OBSOLETE, supersede with this WO.** The exact schema is now known from source for both the shipped consumer and improved-artnet (see Q1 table + the `get_fixtures_ptree()` field lists read directly from both `artnet_consumer.cpp`s above) — no binary-string guessing needed, and WO-229's own T229.3 caveat ("only validate in an isolated/offline environment") is satisfied by simply reading the real parser code instead of inferring one.
- **WO-230 (config-generator support for the native consumer) — STAYS RELEVANT, but retarget to improved-artnet's schema, not the shipped/old one.** If the rebuild proceeds, generate against the richer per-fixture host/port/universe/flux/brightness/mirror schema (Q1 table), not the single-global-host/port shipped schema — building against the old schema now would be throwaway work. WO-230's restart-required opt-in framing and mutual-exclusion-with-JS-pipeline guard are still exactly correct and unaffected by this finding.
- **WO-228 (JS-side hybrid sws_scale sampling) — STAYS as the primary/interim architecture, not superseded.** This is the single most important conclusion of this WO: **improved-artnet does not close the dynamic-config gap** — it makes the native consumer's *sampling quality* strictly better (native sws_scale per-fixture-group, matching/exceeding what WO-228 proposed doing JS-side) but its *operating model* (config-file-only, restart-on-remap) is unchanged. For any rig where operators edit fixture mapping live during a show — this project's stated normal workflow — WO-228's live-reconfigurable hybrid remains the correct near-term investment regardless of whether the C++ rebuild happens. The rebuild and WO-228 are not competing; they solve different problems (native consumer = best answer for a *fixed* rig accepting restarts; JS hybrid = best answer for a *live-edited* rig).
- **WO-231 (perf measurement)** — unaffected either way; still worth doing before/independent of any of this, since it's the baseline any future comparison (native vs. hybrid vs. status quo) would be judged against.
