## 1. Problem (owner-reported)

1. "when cropping in looks editor (crop in effects) there should appear special crop points in the editor so the crop can be done visually" — crop is numeric drag-inputs only.
2. "cropping needs real pixel values and not 0-1 range."
3. "the cropping is also not visible in the editor in gui at all" — layers render uncropped in the editor.
4. "pip borders need to be 'aware' of the cropping so they appear on the actual content and not what it originally was."

## 2. Investigation findings (2026-07-13)

Crop is a mixer effect stored per scene layer in `layer.effects[]`; **both editor render paths and the PIP border geometry read only `layer.fill` and ignore `layer.effects`** — that single fact explains #3 and #4.

- **Definition (0–1 floats):** `client/lib/effect-registry.js:129-142` — `type:'crop'`, params `left/top/right/bottom`, defaults `0,0,1,1`, schema min 0 / max 1 / step 0.01 / 3 decimals. CasparCG itself expects normalized fractions (`MIXER <ch>-<layer> CROP l t r b 0` — serializer `src/caspar/amcp-mixer.js:189-196`; reference `MixerCropParameters`), so **pixels are a UI-layer conversion, not a Caspar change**.
- **Editing UI:** `client/components/inspector-effects.js` — `renderEffectsGroup:177` → `renderParamEditor:27` → `createDragInput:70`; numeric only. Persisted via `sceneState.patchLayer(..., { effects })` from `client/components/inspector-scene-layer.js:202-216`.
- **Value flow:** client AMCP builders `effect-registry.js:299-300` (body) and `:343-344` (raw `MIXER … CROP` line); live apply via `client/lib/effect-apply-live.js`; server REST `src/api/routes-mixer.js:133-134`, `routes-mixer-inspector.js:44-45`; take/timeline pipelines `src/engine/scene-take-lbg-helpers.js:38-39`, `timeline-playback-helpers.js:48-49` (reset `CROP 0 0 1 1 0` at :22).
- **Editor render paths (neither applies crop):**
  - DOM compose editor `client/components/scenes-compose.js` — layer box from `layer.fill` only (:206,:210-216); thumbnail fills the box uncropped (:232-240). Transform handles already exist (`scenes-layer__handles` + 8 `scenes-layer__edges` zones, :299-354) with drag math in `scenes-compose-handlers.js` (`startEdgeResize:190` patches `fill` at :268-270) — the exact pattern crop handles should mirror, writing crop params instead of `fill`.
  - Canvas deck/preview stacks `client/components/preview-canvas-draw-stacks.js` — `drawSceneComposeStack:46` clips to the full fill rect (:131-133), draws image (:136-143), border stroke (:160-162); same in `drawTimelineStack:440-469`.
- **PIP border geometry ignores crop:** `src/engine/pip-overlay-utils.js` — `computePipOverlayPlacement:338` expands the **uncropped** `contentFill` (`expandFillOutward:250-260`; inner hole `innerRectInOverlayNorm:262-274`); `computePipRouterPlacement:374` same. Border thickness is already pixel-based (`outsetPxForPipOverlay:222`). Client feeds it `resolveLayerFillForAmcp` (`client/lib/mixer-fill.js`) via `client/components/inspector-pip-overlay.js:89-98` → `/api/pip-overlay/apply|update` — no crop input anywhere.
- **WO-110 server compose JPEG needs no change** — Caspar renders the real crop, so the server-composed thumbnail is already correct; the gap is purely client-reconstructed geometry + the border rect.

- [x] T158.2 **Show crop in the editor (fix #3).** Canvas path DONE 2026-07-13 (part A): `preview-canvas-draw-stacks.js` `drawSceneComposeStack` + `drawTimelineStack` clip drawn content/status/placeholder to `cropAdjustedRect` and put the layer outline/L# label on the cropped rect; the image keeps the full fill-rect mapping (equivalent to cropping the source rect — MIXER CROP crops the source in place, layer rect unchanged). **DOM path DONE 2026-07-13 (part B):** `scenes-compose.js` now wraps each layer's source content (thumbnail/placeholder/live-thumb) in a new `.scenes-layer__content` child of `.scenes-layer__inner`, separate from the handle buttons (which sit outside the content box via negative offsets and must never be clipped); `cropFromLayer(layer)` (null on no/identity crop) drives a `clip-path: inset(top% right% bottom% left%)` on that wrapper only when a real crop exists — identity/no crop sets no style at all (zero DOM diff). `startCropResize` (T158.3) keeps this clip-path in sync live during a drag.
- [x] T158.3 **Visual crop handles (fix #1).** DONE 2026-07-13 (part B). 8 bracket-style drag zones (`.scenes-layer__crop-handle--n/s/e/w/ne/nw/se/sw`, new `.scenes-layer__crop-handles` container) rendered on the cropped-content outline in `scenes-compose.js`, positioned via inline `left/top/right/bottom` percentages computed straight from the crop fractions (the layer's own box already equals the fill rect, so no pixel math is needed — cropAdjustedRect's percentage convention is reused directly). New `startCropResize` in `scenes-compose-handlers.js`, modeled on `startEdgeResize`, converts pointer delta into a fraction of the layer's own on-screen box (canvas rect × the layer's fill scale) and calls a new pure exported helper `cropDeltaToParams(edge, startCrop, dxFrac, dyFrac, minFrac)` (clamps 0..1, enforces `left<right`/`top<bottom` via a minimum crop window, mirrors `startEdgeResize`'s `minS`) — smoked in isolation (see T158.6). It patches through `sceneState.patchLayer(sceneId, layerIndex, { effects })`, the exact same array-based effects patch the inspector uses (`inspector-scene-layer.js` `onUpdate`), so live-apply / preview-push fire identically to an inspector edit; it lazily creates the `crop` effect entry (identity params) on the first drag if the layer doesn't have one yet, matching `inspector-effects.js`'s param shape. Visual style is bracket-style corner marks + short edge ticks in amber (`--warn`), explicitly distinct from the round blue (`--accent`) rotate/scale handles and the plain (invisible) edge-resize zones. **Activation UX (part-B decision, since the WO left this open):** crop handles auto-show whenever the layer already has a `crop` effect entry (any params, including a freshly-created identity one, so they stay visible across the re-render that follows the first drag); a new third button in the handle bar, `.scenes-layer__handle--crop` ("Toggle crop handles"), lets the operator open/close the crop-handle overlay on any layer, including ones with no crop yet, via `aria-pressed`. The toggle only flips DOM visibility (`.scenes-layer__crop-handles--active`) — it never itself writes a crop effect; that only happens on an actual handle drag, so clicking the toggle and deciding not to crop leaves no data behind. Since `startCropResize` isn't threaded through `scenes-editor.js`'s explicit `opts` wiring (out of scope for this WO), `renderComposeScene` builds a second, throwaway `createComposeDragHandlers(sceneState, schedulePreviewPush)` internally (cheap — pure closures) and uses only its `startCropResize`, leaving the other four handlers exactly as wired by the parent.
