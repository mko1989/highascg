# WO-159 — Screen 2 (ch3) black compose preview: stale JPEG served + blocklist state never reaches the client

**Status:** Implemented (owner/hardware acceptance pending)
**Priority:** High (operator flying blind on screen 2 previews)
**Date:** 2026-07-13
**Source:** `work/todos13.07.26` (owner)
**Related:** WO-144 (compose-preview defects/blocklist — this WO closes its UX gap), WO-57/58 (compose preview), WO-63 (looks deck compose thumbs), WO-71 (look PGM thumbnail cache), WO-155 (stale PRV thumbnail — same pipeline).

## 1. Problem (owner-reported)

> "in the gui the screen 2 (caspar ch3) is displaying black frame on the pgm in compose prv and the current look. this can be linked to the prv issue and is probably rooted in the compose preview jpeg file workflow."

Owner's hunch is right: it is the compose-preview JPEG workflow — but the black frame is a **stale valid JPEG from Jul 5 being served forever**, combined with the WO-144 blocklist state never reaching the client.

## 2. Investigation findings (2026-07-13, live box evidence)

- **ch3's FILE consumer is rejected right now** — `log/caspar_2026-07-13.log:241-242`: `ADD 3-701 FILE media/highascg_preview/ch3.jpg …` → `400 ERROR`. Same for ch2 (:232), ch5 (:252), ch6 (:2771). **Only ch1 attaches OK** (:189-190). The rejecting set is ch2/3/5/6 — wider than the ch3/ch5 recorded in WO-144.
- **A stale `ch3.jpg` (3281 bytes, mtime Jul 5, valid 960×540 JPEG, near-black content) sits on disk and is still served.** `ensureComposePreviewJpgStub` (`src/preview/compose-preview-consumer.js:57-66`) writes a 0-byte stub only if the file is *missing* — it never truncates an existing stale file. The meta/image endpoints only 404 when `size <= 32` (`src/preview/compose-preview-cache.js:154,:208`), so the 3.2 KB stale frame passes and is returned 200 with an ETag. Contrast live `ch1.jpg`: 20 KB, mtime current.
- **The client's blocklist map is effectively always empty.** `drawComposeSnapshotCell` (`client/components/preview-canvas-compose-snapshot.js:235-266`) would show the WO-144 "preview unavailable on ch N" badge (:241-247) — but `_blocklisted` is populated **only** by the one-shot WS transition push (`ingestComposePreviewWs`:96-101). There is no bootstrap on connect/reconnect (`client/lib/app-ws-handlers.js:59,:85,:103` never seeds it; `/api/compose-preview/stats`, which exposes `blocklistedChannels`, is never fetched by the client), and `resetComposePreviewClientCache` (:181-184) wipes it on routing/project changes without re-seeding. Any tab loaded after the rejection paints the stale dark JPEG instead of the badge.
- **"Current look" shows the same black because it is the same path:** `client/components/scenes-editor-deck-thumb.js:47-70` → `resolveLookAirComposeChannel` (`client/lib/look-air-compose-channel.js`) → the same `drawComposeSnapshotCell` with the same ch3 jpeg and the same empty `_blocklisted` map. No separate cache.
- **Upstream trigger unresolved:** ADD args are identical across channels and ch1 succeeds with them, so the args aren't the discriminator — ch2/3/5/6 themselves reject `ADD FILE` (channel/config property in CasparCG). WO-144 detects and blocklists correctly but never remediates the display or the root cause.

## 3. Tasks

- [x] T159.1 **Stop serving stale frames.** On blocklist (and on consumer detach without replacement), truncate or delete `chN.jpg` so the `size <= 32` gate (`compose-preview-cache.js:154,:208`) returns 404 and clients stop painting it. Also consider a max-age staleness gate in the meta endpoint (mtime older than N× pollMs → treat as absent) as defense in depth.
- [x] T159.2 **Bootstrap + re-seed client blocklist state.** Include `blocklistedChannels` in the initial WS hello/state payload (server already computes it — `getComposeConsumerStats`/`getComposeBlocklistStats`), re-push on WS reconnect, and re-apply after `resetComposePreviewClientCache` (:181-184). Result: the WO-144 badge actually shows on every tab, not only ones open at the moment of rejection.
- [x] T159.3 **Root-cause ch2/3/5/6 `ADD FILE` 400.** Compare Caspar channel configs (casparcg.config consumers/format per channel) for ch1 (works) vs ch2/3/5/6 (reject); test manually via AMCP console; check Caspar version's image2/FILE consumer constraints. Fix the config or document the constraint. Update WO-144's rejecting-channel record (was ch3/ch5, now ch2/3/5/6). **Root-caused as a Caspar-restart race** (see work log); config is not the discriminator. Mitigation (clear the blocklist on Caspar reconnect) implemented same day — see T159.3-follow-up entry below.
- [x] T159.4 **Distinguish "no frame yet" from "blocklisted" in the cell** (`preview-canvas-compose-snapshot.js:258-264` dark fill vs :241-247 badge) so operators can tell a starting-up preview from a dead one.
- [x] T159.5 **Smokes:** blocklist → jpeg truncated → meta 404s; WS hello carries blocklist; cache reset re-seeds; extend `tools/smoke/smoke-compose-preview-defects.test.js`.
- [x] T159.6 **Mitigate the T159.3 race: clear the compose-preview blocklist on Caspar reconnect/restart.** A "channel doesn't exist" 400 is only valid for the lifetime of the Caspar instance that produced it; reset the blocklist before the compose-preview consumer re-sync on every reconnect so a transient startup race can no longer become permanent for the rest of the process lifetime.
