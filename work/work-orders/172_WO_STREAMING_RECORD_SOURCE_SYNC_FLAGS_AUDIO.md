## 1. Investigation findings (2026-07-13, confirmed in production logs)

### A. Wrong channel streamed — root cause: missing export kills the live sync

- The persisted source is `config/streaming_channel.json:5` `"videoSource": "program_1"`; attach-mode channel resolution (`src/config/routing-map.js:119-150`) derives the stream channel from it → ch1.
- The function meant to write `videoSource`/`recordOutputs[].source` from the device-graph cable is `applyStreamRecordMappingsFromGraph` (`src/config/device-graph-output-mapping.js:80-164`). It works via the full **"Apply Caspar config" (restart)** path (`device-view-apply.js:250-277`).
- The **no-restart auto-sync after cabling is broken**: `syncDeviceViewToCaspar` (`src/api/device-view-decklink-wiring.js:122-149`) destructures `applyDestinationOutputEdgesToCasparConfig` from `require('./device-view-apply')` — **but `device-view-apply.js:279` only exports `{ buildApplyDryRunPlan, executeApplyPlan }`**. The call is `undefined` → TypeError → swallowed to a warn. Production evidence: `log/highascg-node.log:6977,:7122` — `[device-view] caspar sync: applyDestinationOutputEdgesToCasparConfig is not a function`.
- Net: cabling stream_out to ch3/PGM2 saves only the graph; `videoSource` stays `program_1`; `handlePostRtmp` (`routes-streaming-channel-rtmp.js:56-62,86-87`) resolves fresh but from stale config → `ADD 1 STREAM …`. Record has the same staleness dependency (`record_outputs.json:7`, `resolveRecordSourceChannel` `routes-streaming-channel-shared.js:141-162`).

### B. Restart-flag (orange) policy — under-fires, built on a premise bug A falsifies

- WO-81 policy (`client/lib/caspar-restart-dirty-policy.js:6-35`): stream/record cabling + `streamOutputs`/`recordOutputs` saves must NOT mark dirty — true for encoder settings (read live at ADD time), **false today for source-channel changes** (only the restart-Apply propagates them, per bug A).
- Even after fixing A: `pickSubsystemReloadSnapshot` (`src/config/config-reload-signature.js:29-52`) omits `streamingChannel`/`recordOutputs`/`deviceGraph` (includes only legacy `config.streaming`), so a config save alone never re-triggers routing; and for `dedicatedOutputChannel: true` the `PLAY <streamingCh> route://<src>` only re-issues inside `setupAllRouting` (boot/reconnect, `routing-setup.js:328-340`).
- Regression vs WO-81's own log: `removeStreamOutputConnector`/`removeRecordOutputConnector` (`client/components/device-view-cable.js:352,:367`) still unconditionally `setCasparRestartDirty(true)` although WO-81 T81.3 claims that shipped removed (2026-06-29) — reintroduced/never landed through the file-split refactor.

### C. Audio — two concrete bugs + one dormant

1. **Record uses the documented-bad comma-joined `-filter:a`**: `routes-streaming-channel-shared.js:86` `-filter:a aresample=48000,aformat=…` — the exact syntax `streaming-channel-ffmpeg.js:6-9,:37` documents as causing `400 COMMAND_UNKNOWN_DATA` on some Caspar builds and fixes for RTMP (two chained `-filter:a` passes). The shared file was created fresh in commit `89b1e68` (2026-07-04) and never picked up the fix. **Ranked #1 for "record audio buggy."**
2. **Blind `channel_layouts=stereo` downmix, no layout awareness** (both stream + record): no `-ac`, no source layout/pan — wrong balance/missing channels on non-stereo program buses (this rig's `discrete-8ch` custom layout, `audio-channel-layouts.js:16-19`, `config-generator-audio-xml.js:58-63`; contrast `defaultFfmpegAudioArgs` :20-32 which computes `-ac` properly for other consumers).
3. Dormant (dedicated-channel mode only): `buildStreamingChannel` (`config-generator-consumer-attach.js:429-451`) emits no `<channel-layout>` (sibling `buildHostLiveChannel` :415-416 does) — Caspar-side pre-downmix hazard.

  **T172.1 — export fix, and a second bug found while fixing it.** Exporting `applyDestinationOutputEdgesToCasparConfig` alone was not safe to ship as-is: `syncDeviceViewToCaspar` (the debounced auto-sync fired by `handleAddEdge`/`handleRemoveEdge` for *every* device-graph edge, all connector kinds — `device-view-decklink-wiring.js:118` doc comment "all roles") unconditionally called `applyCasparConfigToDiskAndRestart(ctx)` (the **heavy** write-XML-to-disk-and-restart-the-physical-Caspar-process path) right after the mapping step. Because the export bug made the whole function throw before ever reaching that line, this had been silently dead code — cabling of *any* kind (including DeckLink) currently does **not** auto-restart Caspar in production. Naively fixing only the export would have turned on an automatic full Caspar-server restart ~1.5s after *every single cable edit of any kind*, which is a major, unrequested behavior change on a live show box. Fix: `applyDestinationOutputEdgesToCasparConfig` now returns `casparServerChanged`/`streamChanged`/`recordChanged`/`vcamChanged` (previously only an aggregate `changed`), and `syncDeviceViewToCaspar` only proceeds to the heavy write+restart when `casparServerChanged` is true (i.e. an actual DeckLink/screen-output casparServer key changed) — stream/record/vcam-only syncs return right after the (now-working) config write, matching A172.1 exactly ("no restart needed for the config write itself") and leaving DeckLink/screen-output cabling's restart-on-edit behavior exactly as dead/inert as it is today (restoring it is a separate, bigger decision outside this WO's scope — flagged here for owner awareness: once this ships, DeckLink/screen cabling *will* resume auto-restarting Caspar ~1.5s after each edit, which is the original intended design per the WO-81 dirty-flag policy mirroring the same kind list, but had not been active recently due to the bug).

  Also killed the silent-warn pattern: `scheduleDeviceViewCasparSync`'s catch now logs at `error` (was `warn`) and includes which `stream_out`/`record_out` edges were in the graph at failure time (`summarizeStreamRecordEdgesForLog`); `syncDeviceViewToCaspar` also logs any `warnings` returned by the mapping step (e.g. `multiple_outputs_same_target`) at `warn` with the target/destinationId.
