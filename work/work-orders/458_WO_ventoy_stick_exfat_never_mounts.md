# WO-458 — Ventoy stick: exFAT data volume never mounts (`~/exfat` absent, EBUSY on the raw partition)

**Status: IN PROGRESS (fix + tests landed 2026-08-10; owner QA: reboot a Ventoy stick and confirm `~/exfat` mounts)**

Owner report (2026-08-10): moving stick production from Etcher + trailing exFAT partition
(WO-457) to **Ventoy**. First Ventoy boot on machine `192.168.0.27`: the exFAT half of the stick
"did not get mounted at all". Owner had already relabelled the partition to `HIGHASCGEXF` from
Windows — no effect.

## 1. Investigation

Captured on the booted box (`highascg7579`, live from a Ventoy stick):

```
sdb          29.3G
├─sdb1       29.3G exfat    HIGHASCGEXF            ← by-label target, NOT mounted
│ ├─ventoy    3.5G                    /usr/lib/live/mount/medium
│ └─sdb1     29.3G
└─sdb2         32M

$ ls -l /dev/disk/by-label/
HIGHASCGEXF -> ../../sdb1                          ← label was correct all along
$ blkid /dev/sdb1
/dev/sdb1: LABEL="HIGHASCGEXF" … TYPE="exfat" PARTUUID="6d12a9f1-01"

$ dmsetup ls --tree
sdb1   (252:1)
 └─ (8:17)
ventoy (252:0)
 └─ (8:17)

$ mount -t exfat -o ro /dev/sdb1 /mnt/t
mount: /mnt/t: /dev/sdb1 already mounted or mount point busy.   ← rc=32
```

**Root cause.** On a Ventoy stick the data partition *is* the boot medium. Ventoy maps the booted
ISO's extents out of `sdb1` with device-mapper (`ventoy`, 3.5 G, mounted read-only as iso9660 at
`/run/live/medium`). device-mapper opens its underlying device `O_EXCL`, so **every** `mount(2)`
against `/dev/sdb1` returns `EBUSY` for the whole session. The label was never the problem — which
is exactly why relabelling in Windows changed nothing.

Ventoy also publishes a **second** dm device, `sdb1` (252:1), a 1:1 linear map of the whole
partition — the supported way to reach the Ventoy volume while booted from it. Nothing in the
WO-47 chain knew to use it.

**Second, independent defect** (visible in the same journal). `scripts/exfat/highascg-exfat-boot.sh:46`
was:

```bash
if ! systemctl start --no-block home-casparcg-exfat.mount 2>>"$LOG"; then
        …direct mount fallback…
fi
```

`systemctl start --no-block` returns 0 as soon as the job is *queued*, so the condition is never
true and **the entire direct-mount fallback was dead code**. The boot log proves it — no `WARN:`
line was ever emitted between device detection and the timeout:

```
[…10:22:21] Waiting up to 30s for USB exFAT label HIGHASCGEXF
[…10:22:21] Device present: /dev/sdb1
[…10:23:06] ERROR: /home/casparcg/exfat still not a mount point after mount attempts
```

Meanwhile `home-casparcg-exfat.mount` (generated by `scripts/exfat/install-exfat-units-exfat.sh:13`)
hardcodes `What=/dev/disk/by-label/HIGHASCGEXF`, i.e. the raw partition, and failed on every retry
with `status=32/n/a`. So on a Ventoy stick there was no path to a mount at all.

**Not a fault (owner's second question).** `highascg7579` is not inherited from the eggs host.
`highascg-hardware-hostname.service` runs `apply-hardware-hostname.js` →
`src/system/hardware-identity.js:50`, which derives `highascg####` from the primary NIC MAC and
exists specifically to migrate the ISO's baked-in `highascg-nvidia-*` name
(`LEGACY_HOSTNAME_RE`, `hardware-identity.js:14`). The journal shows the handover: the 12:22:21
lines are still tagged `highascg-nvidia-595`, the 12:23:06 lines `highascg7579`. Working as
designed. (The eggs build host is `highascg-nvidia-595` — that string also survives as the stale
iso9660 label on `sdb2`, see Remains.)

## 2. What was done

`scripts/exfat/highascg-exfat-boot.sh` (+ its playout twin `tools/runtime/wo47-highascg-exfat-boot.sh`,
which ships to boxes because the ISO excludes `~/highascg/scripts/*`):

- **`resolve_usb_dev()`** — new. Walks `/sys/class/block/<part>/holders/dm-*`; a holder qualifies
  only if its sector count **equals the partition's** (this is what rejects the 3.5 G `ventoy` ISO
  map) and it probes `TYPE=exfat`. Returns `/dev/mapper/<name>`, else the raw partition unchanged.
  Sysfs and mapper roots come from `HIGHASCG_SYSFS_BLOCK` / `HIGHASCG_DEV_MAPPER` (production
  defaults) so the selection is testable without root.
- **Mount path rewritten.** `home-casparcg-exfat.mount` is now started **blocking** (its own
  `x-systemd.device-timeout=5` / `mount-timeout=5` bound the wait), and skipped entirely when the
  resolver returned a mapper device — the unit's hardcoded `What=` can only ever address the raw
  partition. A direct `mount` of `$MOUNT_DEV` then runs whenever `$MP` is still not a mountpoint,
  so the fallback is reachable for the first time.

Why direct `mount(8)` is safe for the rest of the chain: systemd tracks `/proc/self/mountinfo`, so
a manual mount at `/home/casparcg/exfat` activates `home-casparcg-exfat.mount` anyway — the
`BindsTo=`/`After=` edges in `highascg-exfat-media-prep.service` and friends still hold.

Why writing to the Ventoy partition is acceptable: the `ventoy` map is read-only and exFAT never
relocates the clusters of an existing file, so the ISO's extents cannot move under it. The one
rule is that the sync pipeline must never touch the ISO itself, which it does not.

**Layout decision — SETTLED, owner 2026-08-10:** *"i dont see a point in creating an additional
partition on the stick when ventoy already does it."* A reserved-space third partition
(Ventoy2Disk → Option → Partition Configuration → "Preserve some space at the end of the disk")
was considered and **rejected**: one Ventoy exFAT partition carries both the ISOs and the operator
data, and the dm-map mount above is what makes that work. Do not re-propose the extra partition.
WO-457's fixed 6 GiB offset simply retires with the Etcher flow — there is no offset under Ventoy.

**Corroboration (owner, same day):** *"the same stick mounted correctly on this machine."* Exactly
what the diagnosis predicts — plugged into a machine that did **not** boot from it, Ventoy creates
no dm mapping, nothing holds the partition, and `/dev/sdb1` mounts normally. The EBUSY is specific
to the box that is running off the stick, which is also the only box where it matters.

## 3. What was VERIFIED to work

- `tools/smoke/smoke-wo458-ventoy-exfat-mount.test.js` (new, registered in the curated
  `tools/ci/run-offline-tests.js` list) — **6/6 pass**. Four cases *execute* the extracted
  resolver under `bash` against a fake sysfs reproducing the exact topology captured above
  (dm-0 `ventoy` 3.5 G + dm-1 `sdb1` 29.3 G) with a stubbed `blkid`: picks the full-size map;
  falls back to raw when the map is not exfat; falls back to raw with no holders; never selects a
  partial-size map even when it probes exfat. Two source guards pin both script copies and assert
  the `--no-block` regression cannot return.
- Full offline suite: **1897 pass / 0 fail / 2 skip** (1899 tests, 253 suites).
- `node tools/ci/check-max-file-lines.js` → 0 files over 500.
- `bash -n` clean on both copies; resolver + mount blocks byte-identical between them (diffed).
- Resolver run against this box's real `/dev/disk/by-label/*` (no dm holders): returns the raw
  device unchanged, and a nonexistent label passes through — no behaviour change off Ventoy.
