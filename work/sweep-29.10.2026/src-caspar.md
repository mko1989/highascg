After `stop()` + >5 s the socket is silently back (`ccg.connected === true`), so the following `start()` → `_ccg.connect()` → `changeConnection` → `_setupSocket()` finds `_connected` already true and emits NO 'connect' event: `_handleConnected` never runs, so no `status` event and the health timer is never restarted. Failing case (dummy server, harness): `start()` (2 status events, health timer on) → `stop()` → wait 6.5 s (server saw a 2nd connection, `ccg.connected` true) → `start()` → 0 status events in 3.5 s, `_healthTimer` null, `isConnected` true. Live trigger: index.js:259-264 — toggling `offline_mode` on then off again after more than 5 s (config reload calls `casparConn.stop()` / `.start()`); the UI never gets a Caspar status or health again until the node restarts. Fix: on `stop()` also set a flag the library cannot override (e.g. `_ccg._connection.on('close', …)` to `socket.destroy()`/clear `_reconnectTimeout`), and on `start()` call `_handleConnected()` itself when `ccg.connected` is already true.
- `BUG` src/caspar/connection-manager.js:348-357 `destroy()` — calls `this._ccg.discard()`, but `CasparCG` overrides `discard()` as the AMCP DISCARD command (`CasparCG.js:505`, not `BasicCasparCGAPI.discard()` which only disconnects and clears timers). Harness (dummy server): after `destroy()` the server receives `REQ sok40 DISCARD`; `ccg.connected` stays true, the socket stays open and the library's `_timeoutTimer` interval keeps running. Only `smoke-state-monitor-health-reconcile.test.js` calls it today, but any future shutdown path leaks the connection and a timer. Fix: `this._ccg._connection.disconnect()` + `clearInterval(this._ccg._timeoutTimer)` (or call the base-class method explicitly).
- `RISK` src/caspar/connection-manager.js:364-383 `reconnect()` — (a) on a manager that was never started, the `host`/`port` setters of `BasicCasparCGAPI` call `changeConnection` → `_setupSocket()` (twice), so the call opens a socket anyway (harness: `reconnect()` on a new manager → server saw a connection, `ccg.connected` true, `manager.isConnected` false). settings-post.js:413 calls it on every Caspar host/port edit, also in offline mode. (b) while connected, `changeConnection` destroys the old socket with its listeners removed, so no 'disconnect' fires: pending waiters are not rejected (they wait out their timeout), `_rawCcgBuffer` keeps the old connection's partial line, and since `_connected` stays true no 'connect' fires either (no `_handleConnected`, no protocol reset). Fix: call `rejectAllPendingAmcpCallbacks` + clear `_rawCcgBuffer` + `protocol.reset()` in `reconnect()`.
- `RISK` src/caspar/connection-manager.js:338-345 — `stop()` also never calls `rejectAllPendingAmcpCallbacks`: it unbinds the 'disconnect' listener before the library emits it (asynchronously, after `close`), so `_handleDisconnected` (which rejects waiters, clears `_rawCcgBuffer`, emits the status) never runs; in-flight commands wait out their 15 s timeout.
- `DEAD` src/caspar/connection-manager.js:102-108 `_onData` — only bound in legacy mode (`_bindSocket` 205). Legacy path kept alive by `smoke-amcp-legacy-transport` and `smoke-state-monitor-health-reconcile`; no production caller sets `HIGHASCG_AMCP_LEGACY_TRANSPORT`. Harmless today, wrong if the legacy path is ever used with non-ASCII media names.
