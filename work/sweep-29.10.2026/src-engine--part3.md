## src/engine/timeline-playback-amcp-send.js
- `BUG-HIGH` src/engine/timeline-playback-amcp-send.js:354-404 — the opacity lead tween in `_sendClipTransport` is always computed for clip-local **0** (`opacitySegmentAtLocalMs(clip, 0, …)`), not for the position the transport actually starts at (`meta.frame` / `ms - clip.startTime`). When the clip is entered mid-way (play from a playhead position, scrub into a clip, Take at a position) the batch still contains `MIXER n-L OPACITY <start> 0` + `MIXER n-L OPACITY <end> <dur> <tween> DEFER`, and the code then records `_lastKfValues[opacity] = startVal` and `_lastKfSegment[opacity-seg] = segIdx(0)` (:399-402), so the per-tick scheduler believes the layer is already correct. Failing case (verified): clip opacity keyframes `(0→0, 1000→1, 5000→1, 6000→0)` on a 30 s clip, `play('T', 25000)` → batch `PLAY 1-212 "C" SEEK 1250 | MIXER 1-212 OPACITY 0 0 | MIXER 1-212 OPACITY 1 25 linear DEFER` then `COMMIT`. At 25 s into the clip the keyframes say opacity 0, the layer fades UP to 1 and stays there: `val` (0) equals the recorded `_lastKfValues` (0), so `valueChanged` is false and no tick ever corrects it. Same for a paused scrub: the picture drifts to full opacity 1 s after the scrub. Fix: only emit the lead tween when `ms - clip.startTime <= 2` (i.e. a genuine clip start); otherwise leave opacity to `_applyKeyedMixerProp`, whose `scheduleLeadTween` branch already handles mid-segment starts correctly.

With `tl.fps = 30` it disagrees with the per-tick path (`tl.fps`), and with the channel at 50p it is half-length (see schedule BUG). Use the channel rate.
- `QUALITY` src/engine/timeline-playback-amcp-send.js:321-329 (loopAlways branch) `STOP` and `PLAY` are two separate AMCP sends while the non-loop branch batches them; the opacity init (`OPACITY <base> 0` when base < 1) is not part of the loopAlways transport and relies on the following `_applyClipMixer` instant write.
