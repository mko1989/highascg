## client/assets/modules/previs/entry.js
- `BUG` client/assets/modules/previs/entry.js:52-55 — the four static imports are root-absolute source paths (`/components/previs-pgm-3d.js`, `/lib/previs-state.js`, `/lib/optional-modules.js`, `/components/previs-settings-modal-pane.js`). They resolve only under the Vite dev server. The box serves the built `dist-web/` (which has no `components/` or `lib/`), where an unknown path falls through the SPA fallback (src/server/http-server.js, ENOENT branch returns index.html). Verified live: `curl -sD- localhost:4200/components/previs-pgm-3d.js` → `200`, `Content-Type: text/html`, body `<!DOCTYPE html>…` (same for `/styles/previs-hud.css`, which src/previs/register.js:60 lists as a module style). A module script with a `text/html` MIME fails to import, so on the production build the previs module never initialises: no 2D/3D toggle on the PGM cell, no "3D Previs" settings tab; the only trace is `[optional-modules] failed to import "/assets/modules/previs/entry.js"` in the browser console (optional-modules.js:111). Previs is enabled on the box (see above), so this fires on every web-client load. Failing case: open the web UI on :4200, console shows the import failure. Even if the paths were fixed, `/lib/optional-modules.js` would be a second module instance next to the bundled one, so `registerOptionalSettingsTab` would write into a different `_state` than `settings-modal.js` reads. Fix options: (a) build the entry through Vite (add it as a rollup input / `import.meta.glob`) so imports bundle, or (b) retire the web previs entry — the native Godot previs (WO-607, WO-665..667) supersedes it. Owner decision.
