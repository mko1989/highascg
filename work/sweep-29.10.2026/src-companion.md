## src/companion/satellite-preview-client.js
- `BUG` src/companion/satellite-preview-client.js:74 + 223-240 + 430 — a destroyed socket's late `close` event clobbers its replacement. `configure()` (line 74) and `releaseSubscribed()` (line 128) call `_closeSocket(true)`, which destroys the socket and nulls `this._socket`; `configure()` then immediately calls `_ensureConnected()` in the same tick, which creates and stores a NEW socket in `this._socket`. The old socket's `close` event fires on the next tick and runs `_onClose()`, which unconditionally sets `this._socket = null`, `_connected = false`, stops the ping. The new socket then receives BEGIN, so `_connected` flips back to true, but `this._socket` stays null, so `_send()` (line ~610, `this._socket?.writable`) silently drops every line: no ADD-SUB, no PING/PONG, no REMOVE-SUB. Failing case (reproduced with sat-race.js): hold a subscription on satellite A (127.0.0.1:26701), then change the Satellite port in Settings (`getSatellitePreviewClient().configure(cfg)` from src/api/settings-post.js:156). Result printed: `after reconfig: connected true socket? false`; server B (26702) logs `conn` but never receives an ADD-SUB, so previews are dead until a restart, while `getStatus()` claims `satelliteConnected:true`. Same shape on any "release last ref then subscribe in the same tick". Fix: capture `const socket` in the `close`/`data` handlers and ignore events when `socket !== this._socket`.
- `BUG` src/companion/satellite-preview-client.js:223-240 `_ensureConnected` — `this._connecting = true` is set, then `net.connect(...)` runs inside a Promise executor. If it throws synchronously (invalid port: `ERR_SOCKET_BAD_PORT`, e.g. satellitePort 70000, which companion-config.js lets through), the promise rejects, `_ensureConnected` throws, and `_connecting` is never reset. Every later call takes the `if (this._connecting)` branch (line ~217) and only waits 5 s for a `ready` that never comes. Reproduced (sat-port2.js): first call with port 70000 throws `ERR_SOCKET_BAD_PORT`; a second call with a valid port and a live satellite server returns `{ok:false, reason:'satellite_not_connected'}` after 5 s, and `_refs` keeps the leaked ref. Recovery needs a node restart. Fix: wrap the connect in try/finally that clears `_connecting`, and delete the ref on failure.
- `BUG` src/companion/satellite-preview-client.js:163-190 `subscribePageSession` — three problems. (1) The row/column range is unbounded: `src/api/routes-companion-preview.js:140-145` passes `payload.rowMax` / `colMax` straight from the POST body, and the loops at line 174 build a `coords` array of (rowMax-rowMin+1)*(colMax-colMin+1) objects before anything is sent. `POST /api/companion/page-preview/subscribe {"page":1,"rowMax":100000,"colMax":100000}` allocates 10^10 entries and kills the node process (OOM) — any authenticated caller can take down playout. Clamp to `pickerGridSize` (or 0..31). (2) When a batch fails (line ~186 `return failed`), cells subscribed by earlier batches stay in `_refs` with count 1 but no session owns them, so nothing ever releases them: the socket stays open and the reconnect loop (lines 435-440) runs forever. (3) `this._sessions.set(sessionId, keys)` overwrites an existing session with the same id without releasing the old keys (the web picker unsubscribes first, but the endpoint accepts a caller-chosen `sessionId`).
- `BUG` src/companion/satellite-preview-client.js:92 `ensureSubscribed` ref-counting vs src/api/routes-companion-preview.js:77 — every `GET /api/companion/button-preview/:p/:r/:c.jpg` calls `ensureSubscribed(...)` (count += 1) and nothing ever calls `releaseSubscribed` for it (grep: `releaseSubscribed` has no caller outside this class; `unsubscribePageSession` releases exactly one count per cell). The picker (client/components/companion-button-picker-modal.js:101, 149) fetches that URL for each of the 64 cells initially and again on every `companion.buttonPreview` push (`refreshCellImage`). After the picker closes, each cell still holds count >= 1, so the 64 ADD-SUBs, the TCP socket and the ping timer stay alive until restart, and Companion keeps pushing SUB-STATE bitmaps that are re-encoded to JPEG, written to disk and broadcast over WS (`companion.buttonPreview`) forever. Fix: make the GET a pure cache read (+ optional one-shot subscribe that is released after the wait), or only count once per session.
- `RISK` src/companion/satellite-preview-client.js:92-112 — a second concurrent `ensureSubscribed` for a key whose first call is still connecting finds the existing ref, bumps the count and returns `{ok:true}` immediately, before a connection or ADD-SUB exists. ## src/companion/satellite-protocol.js
- `QUALITY` src/companion/satellite-protocol.js:20 `parseSatelliteLine` — unescape is two sequential `replace` calls (`\"` → `"` first, then `\\` → `\`). This round-trips `formatSatelliteLine` output for all inputs I tried, but it is not a single-pass decoder: a value containing backslash-then-quote that came from Companion (not from this formatter) decodes differently than a proper left-to-right scan. Use one regex `/\\(["\\])/g → '$1'`.
- `QUALITY` src/companion/satellite-protocol.js:36 `formatSatelliteLine` — an empty-string value is emitted as `KEY=` (the `/[\s"]/` test is false), and `parseSatelliteLine` cannot read it back (`[^\s]+` needs one char), so `X=""` style empties are silently dropped on a round trip. No current caller passes an empty value (ADD-SUB args are all non-empty), so latent.
