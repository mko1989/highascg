## src/stage/glb-write.js

- `RISK` src/stage/glb-write.js:149-155 — on a partial failure (first image read OK, a later one missing) the images already appended stay in `json.bufferViews` but the buffer is re-packed from the ORIGINAL `bin` and `buffers[0].byteLength` is not updated, leaving bufferViews that point past the buffer end. Verified: bin = 84 bytes, resulting views `[[0,36],[36,36],[72,12],[84,8]]`. ## src/stage/mvr-gdtf.js
- `BUG` src/stage/mvr-gdtf.js:58-69 — `GeometryReference` expansion has a depth cap (32) but no cycle or budget limit, so a self-referencing geometry with fan-out multiplies parts as 2^depth. Failing case: a 424-byte description.xml whose geometry `A` contains two `<GeometryReference Geometry="A"/>` → 131,071 parts in 240 ms; with three references the process runs out of memory in seconds (`j47-st1.js gdtf 3` under `--max-old-space-size=512` → FATAL heap OOM, exit 134; one self-reference already yields 17 duplicate parts). `ref !== node` (line 63) only stops the direct self-reference. Reachable by importing an MVR/GDTF from outside (GDTF Share downloads, uploaded .mvr) → Node dies (and the guard `process.exit(1)`s). Fix: track the reference chain (reject a geometry already on the stack) and cap total parts (e.g. 5,000).
## src/stage/mvr-math.js
- `RISK` src/stage/mvr-math.js:18 — `nums()` uses `/-?\d+(?:\.\d+)?…/`, which cannot read a number written without a leading zero: `.5` parses as `5` and `-.25` as `25` (the minus is dropped as well). Verified: `mvrMatrix('{.5,0,0}…{-.25,0,0}')` → x axis `5`, origin `0.025` instead of `-0.00025`; `gdtfMatrix('…-.5…')` → `5`. Neither MVR nor GDTF mandates a leading zero; Vectorworks/MA write `0.5`, but a `%g`-style exporter would silently scale/mirror fixtures. Use `/[-+]?(?:\d+\.?\d*|\.\d+)(?:e[-+]?\d+)?/gi`.
