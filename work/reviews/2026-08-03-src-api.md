### 1. [HIGH] Path traversal in every project-slug route — arbitrary `.json` read, and a persisted write primitive

`src/api/routes-data-project-read.js:63-71`, `:91-99`; `src/api/routes-data-project-handlers.js:170-189`; `src/engine/project-store.js:39-41`

```js
const m = path.match(/^\/api\/project\/file\/([^/]+)(\/download)?$/)
const slug = decodeURIComponent(m[1]).trim()
const project = projectStore.readProjectFile(slug)   // → path.join(PROJECTS_DIR, `${slug}.json`)
```

The HTTP layer never URL-decodes before routing (`src/server/http-server.js:229-265`), so `%2f` survives `[^/]+` and `decodeURIComponent` turns it back into a separator. `projectFilePath()` does a bare `path.join` with no containment check (unlike `resolveSafe()` used for media, or `isValidShaderId()` used for shaders).

**Verified live on this box (read-only GET):**

```
GET /api/project/file/..%2fconfig%2fgeneral  → 200, full contents of config/general.json
```

That file carries `ui.nuclearPasswordHash` (and legacy plaintext `ui.nuclearPassword`, `security.apiToken`) — i.e. the gate for reboot/install/Caspar-control.

The write side is worse (NOT exercised — analysis only). `POST /api/project/load {"slug":"../config/general"}` → `readProjectFile` succeeds (it is valid JSON) → `projectStore.setActiveSlug(persistence, "../config/general")` at line 189. The active slug is persisted, and every subsequent autosave writes through `writeProjectFile(slug)` → `projects/../config/general.json`. A browser tab autosaving every few seconds then overwrites the live server config with a project blob. Same unchecked slug reaches `retireProjectSlug()` (DELETE `/api/project/:slug`, and `/api/project/rename`), which `renameSync`s the target out from under the app.

Failure scenario: anyone on the LAN posts `{"slug":"../config/general"}`; within one autosave cycle `config/general.json` is a project document, and the next restart comes up with default channels/outputs mid-show.

### 2. [HIGH] AMCP command injection — `encoderPreset` / `rtmpServerUrl` are interpolated into `ADD` lines with no newline check

`src/api/routes-streaming-channel-record.js:83-93` → `src/api/routes-streaming-channel-shared.js:94-97`; `src/api/routes-streaming-channel-rtmp.js:85,104-140` → `src/streaming/streaming-channel-ffmpeg.js:79-80`

```js
const preset = String(opts.encoderPreset || 'veryfast').trim().toLowerCase() || 'veryfast'
const video = [`-codec:v ${codec}`, `-preset:v ${preset}`, …].join(' ')
const paramsAfterPath = `${param(fileName)} ${args}`
const res = await ctx.amcp.basic.add(ch, 'FILE', paramsAfterPath, consumerIndex)
```

`param()` (`src/caspar/amcp-utils.js:11-15`) escapes only `\` and `"`; it does not touch `\r`/`\n`, and the transport writes the string verbatim (`src/caspar/amcp-connection-adapter.js:57-68` — it only *appends* `\r\n`, never sanitises). AMCP is line-delimited, so an embedded CRLF is a second command regardless of quoting. Settings persistence validates these fields (`settings-post.js:274-275`), but the request body path does not — `b.encoderPreset` / `b.videoCodec` / `b.rtmpServerUrl` go straight through. (Same root cause as the engine review's finding #1 — one `param()` fix covers both.)

Failure scenario: `POST /api/streaming-channel/record {"action":"start","encoderPreset":"veryfast\r\nKILL"}` → Caspar receives `ADD 5-90 FILE …-preset:v veryfast` then `KILL` → the playout server exits mid-show. Same via `/api/streaming-channel/rtmp` with `rtmpServerUrl` when no project credential is stored (line 85 falls back to the body value).

### 3. [HIGH] Ingest upload write stream has no `error` listener — disk-full or aborted upload kills the process

`src/api/routes-ingest.js:163-183`

```js
const writeStream = fs.createWriteStream(savePath)
file.pipe(writeStream)
writeStream.on('finish', () => { … })
```

Neither `writeStream` nor the busboy `file` stream gets an `'error'` handler. `pipe()` does not forward errors. An unhandled `'error'` event on an `EventEmitter` throws, and `src/bootstrap/process-guards.js:21-29` responds to `uncaughtException` with `process.exit(1)`. (The sibling upload path at line 333-355 registers `fileStream.on('error', reject)` correctly — this one is the straggler.)

Failure scenario: operator drops a large file onto a media volume that hits ENOSPC (the box's media disk is 205 G and the upload cap is 200 G), or closes the browser tab mid-upload → `'error'` on the stream → whole HighAsCG server exits, dropping the AMCP connection and all live control until systemd restarts it.

### 4. [HIGH] Entire USB-ingest API is dead — prefix mismatch between registration and handler

`src/api/router.js:291-294` vs `src/api/routes-usb-ingest.js:345-355`

```js
routes.get('/api/usb-ingest/*', ({ method, path, … }) => routesUsbIngest.handle(method, path, path, …))
```
```js
if (method === 'GET' && p === '/api/usb/drives') return handleGetDrives(ctx)   // never matches
```

`handle()` only compares against `/api/usb/*`, which is never registered; `/api/usb-ingest/*` is registered but never matched inside the handler, so it returns `null` → 404. The client calls the unregistered form (`client/components/usb-import-modal.js:172,224,357,367,388,411`).

**Verified live:** `GET /api/usb/drives` → 404, `GET /api/usb-ingest/drives` → 404, `GET /api/usb/import-status` → 404. The USB import modal is non-functional in its entirety — drive listing, browse, import, cancel, eject. (Note: this is a different layer from WO-413's auto-mount watcher, which works; the *import UI* on top of it does not.)

### 5. [MED] `/api/project/apply-bundle` wipes all persisted state before validating anything, then `process.exit`

`src/api/routes-project.js:184-190, 218-220`

```js
const currentKeys = Object.keys(persistence.getAll())
for (const k of currentKeys) persistence.remove(k)
for (const [k, v] of Object.entries(payload.state)) persistence.set(k, v)
…
```

Destructive-then-populate with no backup and no schema check on `payload.state`. There is no auth gate (registered `requireCaspar:false`, and the route falls through the legacy dispatcher in `router-dispatch.js:105-107`).

Failure scenario: `POST /api/project/apply-bundle {"state":{}}` clears the active-project slug, timer assignments, multiview layouts and every other persisted key, then exits the process 1 s later. Recovery requires re-loading a project by hand.

### 7. [MED] `/api/companion/connection-status` is an unauthenticated SSRF / port-scan primitive

`src/api/routes-companion.js:16-18` → `src/api/companion-connection-status.js:11-58`

```js
const host = String(q.host ?? base.host).trim() || base.host
const port = parseInt(String(q.port ?? base.port), 10) || base.port
```

### 9. [MED] Media-path change moves the live media root non-atomically; failure leaves no media root at all

`src/api/settings-post.js:105-147`

```js
cfg.local_media_path = newPath
…
const bak = mediaLink + '.bak_' + Date.now()
fs.renameSync(mediaLink, bak)
sideEffects.push(`Moved existing media folder to ${bak}`)
…
fs.symlinkSync(newPath, mediaLink)
```

`cfg.local_media_path` is mutated *before* the filesystem work, and the rename/symlink pair is not atomic. If `symlinkSync` throws (EEXIST from a race, EACCES, target on a read-only mount) the `catch` only pushes a warning string — the config is already updated and `/home/casparcg/highascg/media` no longer exists. Caspar has clips open under that path during playout.

Failure scenario: operator changes the media path while a clip is on air → `renameSync` yanks the directory out from under the running consumers, `symlinkSync` fails, `POST /api/settings` returns 200 with a warning, and every media id stops resolving.

### 10. [MED] Over-limit uploads are silently truncated and reported as successful

`src/api/routes-ingest.js:133-136, 144-187`

```js
const bb = busboy({ headers: req.headers, limits: { fileSize: readMaxUploadBytes(), files: 64 } })
…
bb.on('finish', () => { resolve({ status: 200, … body: jsonBody({ ok: true, count: fileCount }) }) })
```

busboy signals a hit limit by emitting `'limit'` on the individual file stream and then ending it — nothing here listens for it. The truncated file still reaches `writeStream`'s `'finish'`, so a `.zip` gets handed to `extractZipSafely` and a media file gets indexed by `runMediaLibraryQueryCycle`. `bb.on('finish')` also fires before the write streams have flushed, so the 200 does not mean the bytes landed.

Failure scenario: a 250 GB master is uploaded against the 200 GB cap → API returns `{ok:true,count:1}`, the file appears in the media library, and it plays out as a truncated clip.

### 12. [LOW] Thumbnail miss path has no negative cache and re-walks the media tree each time

`src/api/routes-media.js:36, 93-97, 136-143` → `src/media/local-media-paths.js:65-102, 159-180`

`failedThumbs` is only populated on the *Caspar* fallback (line 158/161) and only cleared on success — it is never pruned, so it grows without bound across the process lifetime. More importantly, the common local-only miss returns at line 141-143 without recording anything, so every repeat request re-runs `resolveMediaFileOnDisk` → `findFileByStemUnderDir`, a **synchronous** `readdirSync`/`statSync` walk bounded at 8000 entries per base, on the event loop that also drives AMCP. Measured 2.8 ms/miss against this box's current 99-file library; it scales with library size and there is nothing to stop a client (or a stale UI grid) from hammering it.

---

**Overall health.** The routing core is clean — `RouteRegistry` matching, the `requireCaspar` gate, and the auth pre-check in `router-dispatch.js` are all correct, and the codebase shows real discipline in the places that were burned before (AMCP CLEAR coalescing, take-timeout cleanup with a `finally`, atomic config writes, the WO-311 autosave-resurrection guard, credential redaction in the RTMP logs). The consistent weakness is at the *boundary*: values that arrive from a request body or a URL path are frequently trusted to be well-formed. Media paths get `resolveSafe()`, shaders get `isValidShaderId()`, but project slugs get a bare `path.join`, and AMCP encoder/URL fields get `.trim().toLowerCase()` where they need a whitelist. Two things amplify all of it: `enforceAuth` is off by default while the server binds `0.0.0.0`, so every finding above is reachable from any host on the LAN or tailnet; and `uncaughtException` is wired to `process.exit(1)`, so a single missing stream `error` handler is a full outage rather than a logged warning. Fix #1, #2 and #3 before the next show — they are, respectively, a config-destruction primitive, a remote `KILL` of the playout server, and a crash on a routine disk-full. #4 is a straight functionality bug: the USB import feature the UI advertises has never been reachable.
