## Ranked real bugs

### 1. [HIGH] `screen-timers.js` CG ADD/UPDATE lines are malformed AMCP — screen timers cannot actually work against real CasparCG
**File:** `src/engine/screen-timers.js:179` (`assignTimerToScreen` new-assign ADD), `:131` (`assignTimerToScreen` re-assign UPDATE), `:354` (`linesForReAdd` ADD).

Every other CG-line-builder in this codebase (`src/engine/scene-template-cg.js:112`, `src/caspar/amcp-cg.js:26-34,74-77`) follows the real CasparCG AMCP grammar: `CG <ch>-<layer> ADD <cg-layer-index> <template> <play-on-load> <data>`, with the data argument escaped via the shared `param()` helper (backslash-escapes embedded `"`). `screen-timers.js` instead hand-builds:

```js
lines.push(`CG ${channel}-${layer} ADD ${COUNTDOWN_CG_NAME} "${CG_SUBLAYER}" "{""${JSON.stringify(cgPayload).replace(/"/g, '""')}"}"`)
```

Concretely, for `channel=1, layer=980, cgPayload={durationSec:300,mode:'duration'}` this produces:

```
CG 1-980 ADD countdown/countdown "0" "{""{""durationSec"":300,""mode"":""duration""}"}"
```

vs. the correct form used everywhere else in the codebase:

```
CG 1-980 ADD 0 "countdown/countdown" 1 "{\"durationSec\":300,\"mode\":\"duration\"}"
```

Three independent defects, any one of which breaks the command: (a) argument order — the cg-layer index and template name are swapped, and `play-on-load` is missing entirely; (b) the template name `countdown/countdown` (contains `/`) is never quoted, unlike the convention in `scene-template-cg.js:112` (`cgName.includes('/') ? `"${cgName}"` : cgName`); (c) the JSON payload is escaped by doubling `"`→`""` (a CSV/SQL convention), not by the backslash-escaping (`param()`) CasparCG's AMCP tokenizer actually expects — the resulting string is nested/garbled, not valid JSON even if it were reached.

These lines are sent essentially raw: `amcp.batchSendChunked` → `validateBatchLine` (`src/caspar/amcp-batch.js:118`) only checks the command *prefix* (`/^CG\b/i` → always `true`), no argument validation, so the malformed line reaches Caspar unmodified.

**Impact:** assigning a new timer to a screen (`POST /api/timers/assign` first-time), editing settings on an already-assigned timer (`POST /api/timers/assign` re-assign branch — this is exactly what WO-219's new settings editor calls), and the startup/reconnect restore (`linesForReAdd`, wired in `index.js:283-289`) all send broken `CG ADD`/`CG UPDATE`. Only `POST /api/timers/cmd` (start/pause/reset) is unaffected, because `routes-screen-timers.js:274/292` correctly goes through `ctx.amcp.cg.cgUpdate()` instead of hand-building a line.

**Why it wasn't caught:** the only smoke coverage (`tools/smoke/smoke-wo210-screen-timers.test.js`) asserts `line.startsWith('CG')`, `line.includes('countdown/countdown')`, `line.includes('durationSec')` — never the actual well-formed grammar. `routes-screen-timers.js` (the HTTP layer) has zero test files referencing it at all.

**Suggested fix:** replace the hand-built template strings with `ctx.amcp.cg.cgAdd(channel, layer, 0, COUNTDOWN_CG_NAME, true, JSON.stringify(cgPayload))` / `ctx.amcp.cg.cgUpdate(...)` at the call site (matching how `handleCmd` already does it), or if the pure-function-returns-strings design must be kept, reuse `param()` from `src/caspar/amcp-utils.js` and match the exact grammar in `scene-template-cg.js:112`.

### 2. [HIGH] Band guard is missing entirely on `handleCmd` (start/pause/reset) — the one owner-facing safety requirement WO-219 was created for
**File:** `src/api/routes-screen-timers.js:241-343` (`handleCmd`).

WO-219 T219.4 states verbatim: "timer paths may NEVER touch content layers... Add the same validation in routes-screen-timers.js before sending." `isTimerLayer` is defined in `routes-screen-timers.js:36` but called exactly **once**, in `handleAssign` (`:137`). `handleUnassign` and `handleVisible` are indirectly safe because they delegate to `screenTimers.unassignTimer`/`setTimerVisible`, which *do* band-guard internally. `handleCmd`, however, reads `channel`/`layer` straight from `screenTimers.listScreenTimers()` (`:269`) and calls `ctx.amcp.cg.cgUpdate(channel, layer, CG_SUBLAYER, payload)` (`:274`, `:292` on retry) with **no `isTimerLayer` check anywhere in the function, engine or route layer**. A corrupted or legacy registry record (the exact scenario the WO-219 band-guard smokes simulate for every other path, via `persistence.set('screenTimers', ...)` with a hand-edited `layer`) would cause `/api/timers/cmd` — the most frequently invoked endpoint, hit on every Start/Pause/Reset click — to send a `CG UPDATE` to an arbitrary layer outside 980-989, i.e. directly onto a content layer. This is precisely the failure class WO-219 exists to prevent, and precisely the one path it left open.

**Suggested fix:** add an `isTimerLayer(layer)` check (mirroring `handleAssign`) inside the `for (const [screenIdxStr, screenEntry] of Object.entries(record.screens))` loop in `handleCmd`, skip+log and add to `failedScreens` on violation, before either the first `cgUpdate` attempt or the self-heal re-ADD. Also add a smoke test exercising `routes-screen-timers.js` directly (currently zero coverage) with a corrupted-layer record.

### 3. [MEDIUM] `computeDisplayTime` shows full configured duration on pause instead of the frozen remaining time (confirmed pre-existing weak spot)
**File:** `client/components/timer-control-panel.js:69-74`.

```js
if (lastCmd === 'pause') {
    // Paused: show remaining from last computation (server may provide this)
    // For now, fall back to config
    return durationSec || config.durationSec || 0
}
```

The comment admits this is a stopgap. Pressing Pause causes the panel's mirror display to snap back to the *full configured duration* rather than freezing at the actual elapsed-adjusted remaining time — visually indistinguishable from a Reset, even though the on-air CG producer is correctly paused at its true value. This directly contradicts WO-192/205's stated design ("frozen when paused... document the approximation") and is the kind of symptom ("doesn't show the actual timer") the owner has now reported three times (WO-192, WO-205, WO-210). No `pausedAt`/`remainingAtPause` field is tracked anywhere in the server registry (`src/engine/screen-timers.js` `recordTimerCmd` only stores `lastCmd`/`cmdAt`) or the client, so there is no data to compute the true frozen value from without a server-side change.

**Suggested fix:** either (a) have `recordTimerCmd`/the `cmd` handler compute and store `remainingAtCmd` (duration minus elapsed-since-last-start) whenever `cmd==='pause'` is recorded, and have `computeDisplayTime` use that field when `lastCmd==='pause'`; or (b) at minimum, note in the panel UI that paused display is approximate (currently undocumented — the `displayTooltip` string meant to carry exactly this caveat is defined at `timer-control-panel.js:160` but is dead code, never attached to any element — confirmed via `eslint`, `'displayTooltip' is assigned a value but never used`).

### 4. [LOW-MEDIUM] Multi-screen timers: settings-editor save and any config-changing re-assign only pushes `CG UPDATE` to the one screen touched, not to all screens sharing that timer's config
**File:** `src/engine/screen-timers.js:105-140` (`assignTimerToScreen`), `client/components/timer-control-panel.js:501-535` (settings save always targets `Object.keys(timer.screens)[0]`).

`record.config` is a single object shared by a timerId across all its assigned screens, but the re-assign branch of `assignTimerToScreen` only emits a `CG UPDATE` line for `existing.layer` — the one `screenIdx` in the request. If a timer is assigned to screens 0 and 2, saving new settings from the panel (which always targets `Object.keys(timer.screens)[0]`) updates the shared `record.config` in the registry and live-updates screen 0's on-air producer, but screen 2's producer keeps showing the old config until it is individually unassigned/reassigned or the process restarts (at which point `linesForReAdd` would push the now-current shared config to all screens). Not a data-loss bug (the registry itself is consistent) but a real on-air correctness gap for anyone using a timer on more than one screen — plausible given WO-210's whole premise is "assign one timer to multiple screens."

**Suggested fix:** in `assignTimerToScreen`'s config-changed branch, iterate all `record.screens` entries and emit a `CG UPDATE` line per screen when `config` differs from the previous value, not just for the targeted `screenIdx`.

### 5. [LOW] Missing band guard on `assignTimerToScreen`'s re-assign-to-existing-screen branch (mitigated by the route layer, but violates the function's own documented invariant)
**File:** `src/engine/screen-timers.js:117-140`.

Unlike `unassignTimer`, `setTimerVisible`, and `linesForReAdd` (all of which call `isTimerLayer(...)` before emitting a line), the "already assigned to this screen" branch of `assignTimerToScreen` reads `existing.layer` from the registry and pushes a `CG UPDATE` line with **no** `isTimerLayer` check. This is currently harmless end-to-end only because `routes-screen-timers.js:137` re-checks the returned `layer` before sending — but the pure engine function is documented (WO-219 work log: "Added BAND GUARD validation... to all AMCP-returning functions in screen-timers.js") as safe on every line-emitting path, and it isn't; any other/future caller of `assignTimerToScreen` directly (tests, scripts, a different route) would not get this protection. None of the WO-219 band-guard smokes exercise this specific branch (they corrupt the registry then call `unassignTimer`/`setTimerVisible`/`linesForReAdd`/`linesForLookVisibility`, never `assignTimerToScreen`'s re-assign path).

**Suggested fix:** add `if (!isTimerLayer(existing.layer)) { console.warn(...); return { lines: [] } }` before building the CG UPDATE line in that branch, and add a corresponding smoke test.
